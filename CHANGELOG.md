## [1.6.0] - 2026-10-26

### Added

- **co-authored-by-ai**: attributes the commits Pi creates. A `tool_call` hook appends `--trailer "Co-authored-by: AI (Pi/<model>) <noreply@pi.dev>"` to `git commit` commands before they run, so the model that made the commit is named in git history and human commits stay unattributed by construction (the hook only ever sees the agent's own tool calls). Ported from a standalone extension, with the shell-aware core kept intact because that is where the bugs were: appending the flag to the end of the string lands it on the wrong command in `git commit … | tail -5` and on the `rm` of a newline-separated cleanup, slices `git commit -m "fix; thing"` in half, and matches the `git commit` inside `node -e 'const c = "git commit"'`. **Graphite (`gt cc -m "…"`) support was dropped**, and with it the only path that rewrote a commit message rather than appending a flag — that rewriting is how a message containing `$&` got expanded by `String.replace` (reproduced: `-m "cost $& here"` came back with the whole command spliced into its own argument) and how `-am "msg"` silently received no trailer. `gt` is not installed here. **`git commit --amend --no-edit` is no longer skipped** — the skip assumed there was no message to attach to, but there is the reused one, and git's `addIfDifferent` default means re-running the injection never stacks a second trailer (measured on git 2.56.0: three amends, one trailer). Skipping only dropped attribution from the commit-then-amend flow. 49 tests: the trailer contract, the quote-aware splitter/matcher with all four regressions, the handler's skip rules through a fake Pi, and six that **run real git** in a temp repo — the patched string is handed to `bash` and the recorded message read back, because this extension produces a command, not a string (trailer exactly once, a message full of `; && || |` surviving intact, three amends still one trailer, the post-commit cleanup still running). Requires git ≥ 2.32 for `--trailer`; `git -C <dir> commit` and other global-option forms deliberately do not match (documented limit, not an oversight). **Found by using it, not by reading it:** the flag converts one failure mode into a success — `git commit -F -` with an empty stdin aborts with "empty commit message" and exit 1, but with `--trailer` appended the trailer *is* the message, so git exits 0 and commits a message consisting solely of the trailer. That is how the release commit of this very version first landed (subject line: `Co-authored-by: AI (Pi/…)`, body: nothing), and stdin is invisible to a `tool_call` hook, so the response is a pinned test plus a stated limit rather than a guard that cannot exist.

### Changed

- **deps**: pinned `@earendil-works/*` devDependencies to `1.4.0` to match the running Pi install. `tests/test-harness.test.ts` had caught the drift — `npm run typecheck` was checking the extensions against a 1.3.0 API while they execute against 1.4.0 — and said so in the only way that works: `1.3.0 !== 1.4.0`, with instructions.

49 tests in this component, 807 repo-wide. Named a minor release: a new opt-in component, plus the pins the type-check reads — and no existing component changed shape. Enabling it is still a symlink away, so the release changes no one's prompts by itself. Stated rather than hidden: three memory tests are red on this and every checkout more than ten days old — they assert `16 day(s) old` against a `2026-09-30` fixture, which was true only on the 1.5.0 ship date. Neither caused nor fixed here; they need a mocked clock.

## [1.5.0] - 2026-10-16

### Added

- **memory (the bank became readable, and the working state became visible)**: two gaps found by reading this component against the standalone extension it replaced. **(1) Neither working file ever reached a prompt.** `core/activeProjects.md` was referenced by no code at all — it is maintained by hand and by file tools, and the injection mentioned it only inside a staleness warning — and `core/dailyContext.md` was reduced to "N day(s) old", so weeks of open work sat in the bank invisible to every turn while the agent re-derived it from scratch. `before_agent_start` now appends a **working-state block**: `activeProjects.md` verbatim (cut on whole **lines**, never mid-line, file named so `memory_read` gets the rest), and the daily file's **open items**, filtered by the rollover's own classifier (`OPEN_HEADING` / `isCarriedForward`) rather than a second one — if the file is unreadable to the rollover that is one bug to fix, not two to implement. When the list does not fit, selection is **undated first, then newest, then source order**, and the block states how many were dropped. The block's own heading says it is not an entry store and not an authority; its two caps are separate from the 900-token authority budget and the doctor reports what got in (`core/dailyContext.md: 8/9 open items shown, 493 tokens`). **(2) Nothing could read the bank.** `memory_show` answers one key, `memory_search` ranks entries, `memory_doctor` reports health, and the archives under `history/daily/` had no reader at all — so "what were we doing in September" was unanswerable while the evidence sat on disk. Added `memory_read` (any file inside the bank, with its size, the window shown and the offset to continue from — counted in **graphemes**, because a byte offset splits an emoji and a UTF-16 offset splits a ZWJ sequence into a lone surrogate, and neither reads as broken) and `memory_list` (stores, working files and archives in one view, with sizes and dates), and `/memory files [dir]`, which used to print the store listing and so hid most of the bank. Reads are contained to the bank by a rule that is not the entry-path rule: `..`, absolute paths, and a **symlink inside the bank pointing outside it** are all refused, and the walk does not follow links out either. Rehearsed against the live bank, read-only: the block carries 33/33 status lines and 8/9 open items, and the "1 further open item(s) did not fit — the rest with memory_read core/dailyContext.md" line is the point — a memory that is missing is at least visibly missing. 34 more tests (284 in this component): grapheme windows, the symlink-out escape, options surviving the checked read, dropped-line counts, and the tools driven through Pi's own registration surface.

### Fixed

- **memory: a half-written file was invisible.** `applyEdits` leaves a `knowledge/<topic>.md.tmp-<pid>` sibling when the rename throws (it reports "original left untouched", correctly), but nothing ever looked for those files: `memory_doctor` printed "No structural problems found" with one on disk. The doctor now lists leftover temp files and counts them as damage, and the file listing shows them instead of hiding the evidence.

- **picker**: the `memory` catalog entry no longer describes the component as "in development … enable only after removing the standalone memory extension" — it has been live by symlink since v1.4.0, and that line was a release note nobody had updated.

## [1.4.1] - 2026-10-15


### Fixed

- **memory: the automatic daily rollover could be blocked forever by its own archive name.** The rollover runs itself at `session_start` (`/memory daily` only inspects and reports), but on the live bank it had stopped: the archive for 2026-10-14 already existed — written earlier that same day from a file whose date had been *inferred from its mtime* — and the fresh file started for 2026-10-14, when it came to be archived, wanted the same name. The guard said "refusing to overwrite a record" and the daily file sat two days stale, with the staleness notice firing every turn to no effect. Now: identical bytes mean the day is already recorded (nothing is archived twice); any other collision takes the next free slot beside it (`2026-10-14-dailyContext-2.md`) and says so in the notice. Never-overwrite still holds; blocking on a legitimate second record does not.
- **memory: the rollover's own output was partly unreadable to the next rollover — again.** A carried section was rendered as `### Money Manager — Handoff` while the classifier only recognised headings that *exactly* matched an alias, so a second pass called its own carried work an unrecognised heading and dropped it. Alias matching now reads compound titles (group `—` section), and open work is decided by **name or position**: anything under an open heading is open work (`## In Progress` → `### Money Manager`), which the daily **stamping** pass had to learn too — it was stopping at the child heading and leaving items undated, so they could never age. A heading with children now groups instead of swallowing them, so bullets written directly under `## In Progress` are carried as its own work, and the redundant `### In Progress` inside `## In Progress` is gone (the shape self-heals on the next pass).
- **memory: `scripts/daily-rollover.mjs` had its own rollover path** — planning plus a hand-rolled archive-collision branch — which blocked on exactly the case the service archives beside. It now calls the same `service.rollDaily` the extension uses, so there is one rollover with one set of rules.

## [1.4.0] - 2026-10-15

### Added

- **memory (the conflict protocol waits, shows the contest, and never stacks dialogs)**: three failures reported from real use, all fixed at the protocol rather than the surface. **(1) The timer is gone.** Conflict dialogs auto-dismissed after two minutes, which put a clock above the human: an answer nobody had had time to consider was thrown away and the session resumed with a half-answered refusal on screen. Dialogs now wait indefinitely; Esc or cancelling the tool call is how to say "not now", and because **(2) the contest is parked before anyone is asked**, walking away costs nothing — a lost question (step away, displaced dialog, cancelled call, dead UI, an ask that throws) can no longer take the refusal with it. A malformed answer is the opposite case: the question *was* answered, so the queue entry is cleared and the caller is told what was missing instead of the next turn being told nobody was asked. **(3) The session could hang mid-write**: Pi gives extensions one dialog slot, and two parallel `memory_write` calls with rival claims opened a second `ui.select` over the first, leaving the first caller awaiting a dialog that was no longer on screen — reproduced in a real TUI, then fixed by serialising this extension's own dialogs (a second concurrent conflict is parked and reported as "another conflict is already on screen") and by passing every dialog the **tool call's own abort signal** so cancelling the call closes the dialog rather than stranding it. And the resolution dialog was unanswerable as designed: it listed five options without the conflict. It now opens with the whole contest — what the bank says now, what is being written, and the rule that refused it — via one shared `formatContest` used by the queue view, the dialog and the tool result, so no rendering can drift from another; `merge` previews both claims while the replacement is typed; `/memory resolve` without a UI prints the full contest before asking for `--resolve=`; and the per-turn notice carries both claims and the reason rather than a bare id. Verified in a live TUI session: contest shown, no countdown, two parallel conflicts → one dialog and one parked, Esc → parked with the agent continuing in the same turn. 6 more tests (245 in this component).

- **memory (Phase 6 part 2 — daily items carry their own day, so carrying can age)**: whole-section carrying failed on first rehearsal (13 intentions carried, most already finished), so open items now carry a date in the text: `- (2026-10-11) verify the simulator build`. An undated item is stamped with **the day the file claims, never today** — dating Monday's intention on Tuesday would launder it into fresh work — either while carrying or, when nothing rolled over, in a separate pass over open sections that leaves settled work and prose byte for byte. Ageing is per item: past `retireAfterDays` (default 21) an item stops being carried, and a per-section cap (default 30, newest survive) bounds a runaway list; **undated items are never retired**, because unknown age is not an excuse to drop work, and every drop is counted in the rollover notice and remains in the archive. Defaults are deliberately conservative — retiring too early loses real work, so the safe failure is keeping too much one more cycle and saying so — and they are parameters, not baked-in behaviour. Ordering matters and a test caught it: rollover runs **before** stamping so the archive records the file as written, not as the tool rewrote it. Still open and stated plainly: items written by other tools (including the harness's own memory tools) arrive undated and are dated at the next session start, so their age is one day coarse — fixing that means owning the daily append path or agreeing the item grammar with whatever writes it. Using the output as input found two defects that reading the code did not: provenance was written **inside the heading** (`### Next Steps (from 2026-10-13, 11 days old)`), so the next pass no longer recognised it as open work and the stamp pass silently did nothing to the file the rollover had just written — annotations now go in the body as a single line, stripped and rewritten each time (otherwise provenance stacks up like a game of telephone), and heading normalisation tolerates the old format and hand-edited variants; and a section whose items had all aged out was carried as an empty shell, while prose under an open heading was dropped even though a 'run the gate:' line plus a command block is open work. Verified end to end on the live bank: the first session after cutover dated 17 open items in one pass, including under a heading the earlier format had written. And the fresh file's shape is a contract, not a preference: the rollover wrote a file without the top-level sections the harness's own memory tools append to, and they failed outright — a format only the rollover can read is a private format, and the day's work comes back unreadable to the thing that writes it. Output is now fixed and documented (`## In Progress` with grouping one level down, then `## Completed`, `## Key Decisions`, `## Notes`), and the live bank was brought into that shape by hand. 17 more tests (239 in this component, 712 repo-wide)

- **memory (new component, Phase 5b-1b — migration tooling follows the human decisions, still dry-run only)**: bullet-heavy sections split into one entry per claim (the asymmetry decides: an over-granular entry is reviewable and mergeable, a section hiding four claims behind one heading makes the gate blind), with examples and code-token definitions merged into the claim they qualify and fenced code kept with its block; `kind` and `scope` judged per claim. Split keys are named, not truncated sentences — the code token the claim is about, else significant words minus connectives, else a visibly-placeholder `claim-N`. Two sibling claims with the same leading words are flagged `similar-claim` because they get different keys and the gate cannot see them as rivals. A heading that is already an assertion key is left alone: re-reading an entry's `- kind:` / `- asOf:` lines as prose invents claims out of its own metadata, which is what a second dry run on a half-migrated bank would otherwise do (a keyed heading with a non-entry body is reported as broken). In-place rewrite consumes the prose (`prepareMigrationStore`) because the renderer would otherwise dress `## Applies to` up as a claim with a `kind:` field, while entries with real keys are preserved — a migration that silently deleted a hand-written claim would be the worst bug here — and a proposal landing on such a claim is stopped by the collision guard rather than allowed through as an amendment, since a migration does not own it. `--preview <dir>` writes the exact bytes the gate would produce (reading the migrated file is the only review that counts), `--move "a => b"` records a human's file-move decision without performing one, and the report separates headings that became entries from prose not carried over. Bugs caught by simulation rather than review: `entry.scope` is a parsed object, so the collision guard was comparing `global` to `[object Object]` and silently never firing; flags accumulated once per sibling; split siblings were misreported as "same heading in another file"; `--move` swallowed the next CLI flag as its reason. Dry run of the live bank: 23 claims from 10 sections, 0 conflicts, 0 collisions, 0 rejected, no new store violations; decisions recorded — split sections, replace prose in place with a mandatory backup, `knowledge/implementation-plan.md` out of `knowledge/` and into `core/`. 10 more tests (197 in this component, 673 repo-wide)

- **memory (new component, Phase 5b-1 — migration tooling, dry run only)**: `migrate.ts` turns prose knowledge files into *proposed* entries and changes nothing on disk. Three rules: nothing is dropped silently (every skipped file and section is reported with its reason); inferred provenance says it is inferred (an `asOf` from a file mtime is printed as such, because an `asOf` that looks authoritative decides authority); every inference carries the cue that produced it. Not entries: paths outside `knowledge/` (core/ and history/ are working state and dated history), files that read as status snapshots (phases, `COMPLETE`, branch names), structural headings matched **whole** so `## Notes` is scaffolding while `## Background colour` is a claim — a prefix match ate the latter in the first draft — bodyless sections, and `## Source`, folded into `source:` instead of becoming a claim about attribution. Keys are `<file-topic>.<slug(heading)>` with apostrophes treated as in-word punctuation (`Don't push` → `dont-push`); two headings slugging to one key are reported for a human to name, never auto-renamed. The dry run **is** the gate rather than a preview of it: `simulateMigration` folds proposals through `decide` against a store that grows per accepted write, so the report answers whether the writes would be admitted, renders with the store's own serializer, and re-running a migration is a no-op. That simulation caught a hazard from an unexpected direction: the gate allows a write to *amend* an entry it owns — rewording your own claim is authoring — so two prose sections that slugify to one key would silently rewrite each other, with no continuous authorship between them to make that legitimate; batch collisions are now stopped before the gate sees them. `scripts/migrate-report.mjs --bank <dir> --out <file>` prints the plan and has no `--apply` flag on purpose. Dry run of the live bank: 8 files read, 10 proposals, 0 conflicts, 0 collisions, no new store violations; 4 files and 3 sections skipped with reasons; open human decisions on 6 `needs-split` sections, 2 unnamed "this repo" scopes, an mtime-derived 2026-05-02 for a rule older than its file, `knowledge/implementation-plan.md` recommended out of `knowledge/`, and in-place replacement vs staged targets. 17 more tests (180 in this component, 663 repo-wide)

- **memory (new component, Phase 5a — wired, still not enabled)**: the Pi surface. `implementation.ts` registers `memory_write`, `memory_show`, `memory_search` and `memory_doctor`, the `/memory doctor|pending|resolve|show|files` command, and the `before_agent_start` injection hook — all delegating to `service.ts`, which holds the behaviour with no pi types so it is testable without a session. Conflict handling has exactly three shapes: nobody can be asked (print/json/rpc) so the refusal is parked and the caller is told how to answer it; a human is asked inside the same call (select for the resolution, input for merged text, one line of "why" recorded as `resolution:` provenance) and their answer becomes a second gate call; a human is asked and dismisses, so the refusal is parked and nothing is written. Dialogs carry the abort signal and a 2-minute timeout, because a dialog nobody dismisses must not hang a turn — timeout, dismiss and abort are all the same outcome as having no UI. Unanswered conflicts are injected on every turn, `/memory pending` lists them, and `/memory resolve <id>` without a UI requires an explicit `--resolve=`: a suggestion is never applied by default. `fs-store.ts` is the only module that touches disk (bank default `~/.pi/memory`, `PI_MEMORY_DIR` honoured, writes are the gate's rendered bytes via temp-file + rename, path escapes refused); `pending.ts` stores refusals as JSON that replays through the gate verbatim rather than prose that would have to be re-parsed. A single-instance guard refuses to register anything when a real `memory` directory is loaded — verified in a real Pi session, where it fired exactly as designed against the live standalone extension. Bugs caught while wiring: answering a contest through the tool left its queue entry behind, and the same happened on the answered-via-dialog path, in both cases leaving `/memory doctor` reporting a conflict that had already been settled. Catalog description now says what enabling it would actually do. 47 more tests (163 in this component, 646 repo-wide), driving the extension through Pi's own registration surface against scratch banks so no test can touch the live memory bank
- **memory (new component, Phase 4 of 6 — inert)**: recall and injection (`inject.ts`) — the read path now produces prompt text. Retrieval picks candidates, the resolver still picks truth: BM25 over entries with pinned parameters (`k1 1.2`, `b 0.75`, heading/key terms ×3), query terms treated as a set, and `kind`/`scope`/`status` values deliberately unscored so the words `rule`, `global` and `active` cannot drag an unrelated entry into the prompt. Stale claims stay candidates so a hit on a retired rule is answered with the rule that replaced it, and a contested identity is reported even when retrieval only surfaced one side — authority is a property of the store, not of what recall happened to find. **The retrieval-index question is closed with measurements, not preferences**: a `WeakMap` memo keyed by the store object makes recall 0.1 ms at this bank's real size (22 knowledge headings), 0.5 ms at 1 000 entries and 2.6 ms at 5 000 — 8–14× faster than a cold scan with no invalidation rule to get wrong — so no search dependency and no on-disk index; MiniSearch would be a second memory implementation for no measured gain, and qmd's 1–2 s hybrid search is already known too slow for per-turn injection (the live extension uses it only for explicit searches). Budget: `ceil(chars/4)` token estimate, 900 tokens of entry content with per-kind caps so facts cannot crowd out rules, entries that do not fit are skipped rather than truncated and are named in the text, and selection keeps looking after a skip. Presentation is canonical (kind, then key) rather than retrieval order, so a scorer tweak cannot reshuffle the prompt and output is byte-identical for a given store + query + context; each line carries `kind · scope · asOf` and never a score. 26 more tests, plus `scripts/bench-recall.mjs` which prints the measured curve
- **memory (new component, Phase 3 of 6 — inert)**: the write path's admission gate (`gate.ts`), where the invariant stops being a rule and becomes a refusal. `decide(store, request)` is pure — parsed topic files in, rendered file contents out; it never writes and never reads a clock. The boundary that keeps ordinary authoring usable: an incoming heading that names an existing entry **amends** it, while a different heading on the same identity (`key` + `scope`) that is already live **anywhere in the store** is a rival and is refused with nothing written — three files each holding `ui.background` is one identity with three claims, which is exactly the bug this component exists to prevent. Resolutions (`supersede`, `merge`, `withdraw`, `keep-both-flagged`, `discard`) are a second explicit call carrying a `conflictId` derived from the identity, the live claims and the incoming text, so a decision can never be applied to a state nobody was shown; `supersede` rewrites every file holding a rival and records qualified `path#heading` references, because two topic files can hold the same heading. Provenance is written down rather than remembered (`resolution: supersede — <why>`, `amendedFrom`, `withdrawnOn`, `contestedWith`). 21 more tests, each applied, re-parsed and re-resolved: a rival the gate accepts never survives to the read path, and keep-both-flagged correctly makes the identity go dark. Two latent bugs fixed on the way: `renderEntry` silently dropped `supersededBy` and any provenance field, and supersede-chain auditing assumed headings were unique across files
- **memory (new component, Phase 2 of 6 — inert)**: the resolver that turns the entry schema into an enforceable rule. Retrieval picks candidates; `resolver.ts` picks the authority in two gates — one authority *within* an identity (key + scope), then one authority *per assertion key* across `project`/`path`/`global` scopes for the current context, so a global default and a project override never arrive together for the model to referee. A contested identity **fails closed**: nothing is injected, and the conflict is reported with its `bestCandidate` (a suggestion for the human, never an answer). A hit on a superseded claim **redirects** to the claim that replaced it rather than quoting a dead rule or going silent, and everything shadowed or out of scope is recorded rather than discarded. Scope matching is standard minimatch with pinned options (`dot: true`, `nonegate`, `nocomment`) so a scope pattern behaves as a matcher rather than an ignore file. 36 tests, including three invariant sweeps over 200 generated stores: at most one injectable authority per identity, every entry accounted for exactly once, and an injected set that never contains a non-authority, never contains two entries for one key, and never depends on candidate order
- **memory (Phase 1)**: the entry schema and topic-file parser for the memory extension that will replace the standalone `memory` bank. Knowledge is keyed by *assertion* (`## ui.background` with `kind`/`scope`/`asOf`/`source`/`status`), so identity is computable and a conflict becomes "two active claims on one key+scope" instead of a similarity tie nobody can break: three files disagreeing about a UI background color score `14.40 / 14.40 / 14.30` under the old index and all three get injected. `parseTopicFile` never throws — malformed scopes, statuses and dates are errors that make an entry non-injectable rather than silently defaulting (a bad `scope` never becomes `global`), and `compareAuthority` fixes a deterministic order (specificity → `asOf` desc → key/heading) that contains no similarity term at all. A malformed entry never marks its well-formed sibling a duplicate. 30 tests plus a pin that the unfinished factory registers nothing, so it cannot compete with the live memory extension. Listed in the picker catalog to keep the catalog guard honest; not symlinked, so nothing is enabled

### Changed

- **dependencies**: `minimatch` added as a runtime dependency, used only by the memory component for `scope: path:<glob>` matching. Justification (AGENTS.md §6): glob edge cases — dotfile paths, `**` crossing segments, leading `!`/`#` — misclassify a scope *silently*, the exact failure class this component exists to remove, so a hand-rolled matcher would be extra surface to defend rather than less. The option choices (`dot: true`, `nonegate`, `nocomment`, case-sensitive) are pinned by tests rather than assumed. Going forward every runtime dependency needs a matching justification line in its component's README

## [1.3.0] - 2026-10-13
